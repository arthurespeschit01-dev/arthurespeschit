# Start dates, current work and recurring cycles

This replaces the visibility and recurrence rules in the previous task workspace notes. Existing records and statuses are retained; the migration does not rewrite, consolidate or delete historical or future tasks.

The server uses the current date in America/Sao_Paulo. `agency_tasks_list` provides owner-only active, planning and history scopes. Daily table/board, the home dashboard and task notifications use active scope: the task is open and its start date has arrived. Without a start date the deadline acts as its availability date; undated open tasks remain available. A future start takes precedence over an already past deadline. All completed/canceled tasks belong in History, including those completed today. Status summary counts match daily eligibility, with a separate planned count.

Planning is an explicit calendar/phone agenda, with one placement per saved occurrence on its start date (or deadline when no start exists). It never paints an occurrence across every day of a range or generates speculative instances. Future tasks remain editable there. Reopened predecessors block descendants from daily work, preventing two active occurrences in the same chain.

Completing an occurrence creates one successor atomically in a database trigger for every write path. The unique predecessor reference makes replay/reopening idempotent. The next cycle is strictly after both today and the completed occurrence's scheduled date, so late completion skips missed cycles instead of creating a backlog. Calendar calculations preserve the original phase for weekly intervals, selected weekdays/month days and monthly/yearly month-end clamping. The start-to-delivery duration is preserved, as are responsible account, area and subtask titles, with subtask completion reset. Changing the schedule resets its anchor; old chains derive their anchor from existing ancestors without updating them. No cron mass-creates instances.

Responsible person is selected from the authenticated user's own account plus an unassigned option. Existing free-text names remain visible as an unselectable legacy value. The new responsible UUID must match the task owner. Area supports Tráfego, Design, Edição, Conteúdo, Atendimento, Comercial, Gestão and Outros, with editing, filtering and grouping. Duplication and recurrence carry both fields.

Status controls use an accessible colored custom menu for each option: slate for pending, amber for in progress, green for done and rose for canceled. The status values stored in the database remain unchanged. The task header uses compact summary chips and one toolbar, with advanced filters in a popover so they do not push task rows down. Phone controls retain the same functions.

Verification: `task-schedule-db.mjs` covers start-day gating, counts, one successor, overdue completion, reopened predecessors, direct/RPC writes, month-end phase and duration, own-account assignment, area propagation, anonymous/cross-owner denial and legacy-row preservation. `task-schedule-browser.mjs` covers home dashboard, table, board, history, planning dates, day release, color distinctions, account selection, grouping and phone layout. Existing task workflow, DB and unit tests remain in the scripts.
