# Private WhatsApp media

W-API's download endpoint requires the webhook's `mediaKey`, `directPath`, media type and MIME type and returns a temporary download link. The old implementation sent only `messageId` and expected base64, leaving every attachment unavailable. The media descriptor is recovered only from the server-private event stream for the matching instance, connected sender and provider message ID.

Received media is downloaded with bounded streams (32 MB), accepted MIME types and HTTPS host/redirect validation. Provider credentials are sent only to W-API's download endpoint, never to a returned file URL. HTML/SVG error payloads are rejected. Vértice stores files in its existing private WhatsApp bucket. Central copies shared media to its own private bucket, or downloads with its own descriptor for standalone instances. Central's descriptor and recovery metadata are inaccessible to browser roles. Both frontends obtain one-hour signed links only through authenticated, sender-scoped APIs. Clients cannot supply storage paths, remote URLs or download keys.

Message rows and their timestamps are retained when media retrieval fails. Recovery state and a lease make repeated views/webhooks idempotent. New webhooks, scheduled reconciliation and opening a media message can recover files. Historical known-account media is queued automatically. Old files without source/descriptor information or no longer retained by the provider remain explicitly unavailable, with retry controls; availability is not fabricated. Uploads do not resend messages to WhatsApp or alter CRM stages. No cleanup deletes are introduced.

Both inboxes render photos, native audio controls, video and document links. Captions are retained. Photo links open a larger version, media links refresh on retry and each client limits concurrent requests. Signed links and encryption/download metadata stay out of logs.

Verification: unit tests cover descriptor shape, the correct provider request contract, bounded binary/base64 downloads, redirects/host rejection, error-page rejection, private storage and expiring signatures. Browser tests use a real synthetic PCM WAV and PNG to verify decoding/playback and image rendering in both apps, no send requests and mobile width. Central's migration tests verify unchanged history, a private bucket and denied browser access to descriptors/recovery RPCs. Tests do not send customer messages.
