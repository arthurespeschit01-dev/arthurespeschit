# WhatsApp history synchronization repair

The Central→Vértice mirror called a security-invoker RPC with an empty search path. Vértice's BEFORE INSERT trigger resolved `leads` without a schema, causing PostgreSQL 42P01 errors and leaving confirmed sends in the durable mirror queue. The Vértice migration qualifies table names and fixes the trigger's search path to `public` for compatibility with its text-normalization helpers. Its after-insert preview guard preserves newer conversation summaries/unread state when older pending messages are replayed. No historical rows are deleted or rewritten by the migration.

W-API emits content-bearing phone sends as `webhookDelivery`. Both parsers previously classified all delivery events as receipts. They now accept content-bearing outgoing delivery events and still reject bare receipts. Vértice forwards the event to Central, stores the outgoing history, and keeps outgoing events out of the inbound AI/n8n pipeline to prevent reply loops. Existing inbound forwarding stays active.

Both connection/configuration actions register received and delivery events at the same existing callback. Central's scheduled reconciliation also verifies/enables the delivery event once on an existing authorized receiving integration. It refuses unrelated receiving/delivery callbacks and verifies the provider's resulting settings before recording activation. No message-send API is used for activation or mirroring. Callback capabilities and provider credentials stay server-side.

Failed mirror attempts retain their history record and now expose sanitized technical state instead of silently claiming a healthy sync. Retry is idempotent per sender/provider and never resends the WhatsApp message. Sender-account isolation and the forms-only commercial CRM remain unchanged. Old phone messages can only be recovered if the provider retained their events; activation does not invent unavailable history.

Verification: Vértice's `mirror-trigger-db.mjs` reproduces the original trigger failure with the real RPC search-path behavior, checks preserved rows and previews, and verifies idempotent acceptance and role restrictions. Its API tests cover received/delivery registration, forwarding, outgoing phone history, ignored receipts and prevention of outbound AI loops. Central's Deno tests cover activation verification/conflicts and durable mirror retries, while normalization tests cover actual W-API delivery shapes and nested keys. Real customer test messages are not sent.
